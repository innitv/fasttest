## 0. Итог одной фразой

Репозиторий инженерно здоров: схема темы — настоящий источник правды, пропуск регистрации архетипа ловит компилятор, уроки фиксируются дисциплинированно (11 правок `FIXES.md` на 13 тем). Слабое место одно и системное: **всё, что ведётся перечнем вручную, отстаёт** — три темы из тринадцати выпали из проверки кегля полей, а нумерация диагнозов разъехалась до двух «багов 13».

## 2. Разбор по элементам

### 2.1. Схема темы (`tenant.schema.ts`) — сильнейшая часть

**Роль.** Единственный источник правды о том, что такое тема: перечень архетипов, оси оформления, клампы порогов, контент экранов.

**Сильные стороны.** Новый архетип нельзя завести наполовину: `Record<Archetype, …>` в `ScreenHost`, `build-theme` и `bank-payload` заставляют компилятор потребовать все три регистрации. Список архетипов для `?archetype=` выводится из схемы, а не пишется второй рукой — в README прямо записано, почему («второй список расходился молча»). Клампы несут обоснование в комментарии, а не только число.

**Пробелы.** Единственная незакрытая регистрация — маршрут в `App.tsx`: его отсутствие не ловит никто, ссылка просто не заведётся. README это честно называет, машинной проверки нет.

### 2.2. Приёмка (`verify`, `check:mobile`, `check:theme`)

**Роль.** Сторожит инварианты кода: границу темы, зону нажатия, кегль полей, поведение пуша, системные зоны.

**Сильные стороны.** Норма «новая проверка обязана иметь негативный контроль» записана в `CLAUDE.md` и соблюдалась: проверка кегля полей после дефекта получила третьим элементом ожидание «есть поля или нет», чтобы пустой набор не засчитывался за успех (`FIXES.md`, баг 14). Мобильная приёмка идёт в профиле устройства с настоящими тач-жестами, а не в узком десктопном вьюпорте.

**Пробелы.** См. находку P1-1: перечень маршрутов пополняется руками и уже отстал.

### 2.3. Документация

**Роль.** `CLAUDE.md` — индекс правил (грузится автоматически), `README.md` — порядок работы, `FIXES.md` — диагнозы дефектов.

**Сильные стороны.** Разделение осмысленное и соблюдается: механика — в README, диагнозы — в FIXES, границы — в CLAUDE.md. Каждый пункт чек-листа со звёздочкой означает «появился после того, как его пропуск стоил переделки» — редкая честность, по которой видно цену правила.

**Пробелы.** `FIXES.md` — 859 строк, 16 диагнозов, **без оглавления**. Найти нужный можно только чтением целиком или грепом по номеру, а номера ведутся вручную (см. P1-2).

### 2.4. Агентная инфраструктура

**Роль.** Должна доносить повторяемую процедуру до исполнителя.

**Состояние.** Отсутствует полностью: ни навыков, ни команд, ни `launch.json`. Вся процедура живёт в README и подключается одной ссылкой из `CLAUDE.md`.

**Сравнение с внешними практиками.** У [shadcn-ui/ui](https://github.com/shadcn-ui/ui) каталог `.claude` лежит в корне репозитория рядом с `.github` и `.vscode` — агентная конфигурация версионируется вместе с кодом. Официальный [anthropics/skills](https://github.com/anthropics/skills) показывает минимальный контракт навыка: папка + `SKILL.md` с `name`/`description` во фронтматтере, инструкции в теле, вспомогательные скрипты и ресурсы рядом. Ни там, ни там нет требования дробить — структура плоская.

## 3. Находки

### P1-1. Три темы из тринадцати выпали из проверки кегля полей

**Верификация — замером, а не по схеме.** Поднят dev-сервер, каждый маршрут открыт в профиле 390×844, поле раскрыто тем же способом, каким это делает сама проверка:

| Маршрут | В списке `ROUTES` | Полей фактически |
|---|---|---|
| `/voroh` | да (контроль) | 5 — `full_name`, `phone`, `email`, `promo`, `phone-input` |
| `/voroh-light` | **нет** | **5 — те же самые** |
| `/uchi` | **нет** | **1 — `phone-input`** |
| `/yes-atlas` | **нет** | 0 |

`/voroh-light` — та же тема, что `/voroh`, тот же архетип, тот же набор полей; один маршрут сторожится, второй нет. У `/yes-atlas` полей нет по устройству, но и записи с ожиданием `false` тоже нет — появление поля никто не заметит.

Сейчас кегли у всех 16 px, то есть дефекта нет. Нет **сторожа**: любая правка этих тем пройдёт мимо приёмки, а именно от этого правило и заводилось (`FIXES.md`, баг 7 — Safari зумит страницу при фокусе на поле мельче 16).

**Причина системная.** README, шаг 6, сам предупреждает: «маршрут, не внесённый в список, не проверяется, и поле с кеглем ниже 16 px уезжает в прод при полностью зелёной приёмке». Правило известно, записано, и всё равно нарушено трижды — потому что исполняется вручную.

### P1-2. Два диагноза под номером 13; ссылки на них означали разное

`FIXES.md` содержал `## Баг 13 — цвет кнопки, измеренный у донора, ронял тему на экран диагностики` и `## Баг 13 — гарнитура снята с body` одновременно. При этом `CLAUDE.md:55` ссылается на «баг 13» в значении первого, а `README.md:172` — в значении второго.

**Исправлено в ходе аудита:** второй переименован в «Баг 16», ссылка в README обновлена. Проверено: `grep "баг 1[3-6]"` даёт три ссылки, каждая ведёт к своему разделу.

**Причина та же, что у P1-1:** нумерация ведётся вручную, машинной проверки на дубль нет.

### P2-1. `FIXES.md` без оглавления

71 КБ, 16 диагнозов. Модель либо читает целиком (дорого на каждой сессии), либо не читает вовсе — и тогда грабли повторяются, ради чего файл и ведётся. Дешёвое лечение: таблица «номер — симптом — где проявляется» в начале файла, чтобы найти нужный диагноз можно было по симптому, а не по номеру.

### P2-2. Маршрут темы в `App.tsx` не проверяется ничем

Единственная из пяти регистраций архетипа, которую не сторожит компилятор. Тема, заведённая без маршрута, существует, проходит сборку и недоступна по ссылке.

## 4. Что уместно оформить навыком, а что нет

Ключевая оговорка: `CLAUDE.md` здесь грузится автоматически и уже выполняет половину работы навыка. Поэтому выигрыш не в том, «дойдёт ли правило», а в структуре и в подключении по описанию задачи.

### Стоит: один навык на цикл темы

Процедура «от снятия донора до сдачи» пройдена **тринадцать раз** и занимает в README два раздела (чек-лист 50 строк + подробности 120). Это ровно то, что навык описывает лучше документа: последовательность с гейтами, где половина пунктов появилась после переделки.

Что в него входит: снятие донора страницей целиком → решение об архетипе (ось структуры, не оформления) → четыре записи нового архетипа → сборка с порогами схемы → **показ человеку сразу после первой сборки** → сдача (маршрут в проверку, таблицы README, четыре команды приёмки, уборка).

Что в него **не** входит и остаётся ссылкой: обход образца и замеры — это переносимое ремесло из `/ui-craft:reference-check` (включая типографику, §3.4.3), дублировать его в проекте нельзя.

### Стоит: команда приёмки

Четыре команды в фиксированном порядке, из которых одна требует отдельного окна (`yarn preview` перед `verify`). Это механическая последовательность, которую человек и агент выполняют одинаково, — кандидат в `/приёмка`, а не в навык.

### Не стоит

- **Отдельный навык на снятие донора** — дублирование `/ui-craft:reference-check`.
- **Навык на диагностику дефектов** — `FIXES.md` не процедура, а справочник; ему нужно оглавление (P2-1), а не оболочка навыка.
- **Наращивание числа навыков вообще**: у проекта один основной процесс, и дробить его на «снятие», «сборку», «сдачу» значит получить три файла, которые расходятся. Первоисточник Anthropic про навыки прямо советует держать связанное знание в одном `SKILL.md`.

## 5. Отложено на решение владельца

Структурные изменения молча не вносятся:

1. **Заводить ли `.claude/` в репозитории** (навык цикла темы + команда приёмки). Цена — новая сущность в проекте без агентной инфраструктуры; выигрыш — процедура подключается по описанию задачи, а не только по ссылке из индекса.
2. **Закрывать ли P1-1 машинно**: вывести список маршрутов проверки из `PATH_ROUTES` вместо ручного перечня, чтобы новая тема попадала в приёмку автоматически, а её ожидание по полям задавалось явно.
3. **Проверять ли номера диагнозов** (P1-2) и **маршрут темы** (P2-2) отдельной проверкой.

## 7. Закрыто по решению владельца (2026-08-21)

Навык маршрутизирует и не пересказывает README: порядок остаётся одной копией.

**P1-1 закрыт машинно.** Проверка кегля полей теперь сверяет свой перечень с
`PATH_ROUTES` в `App.tsx` и падает, называя невнесённые маршруты поимённо.
Негативный контроль — фактический: до внесения тем вывод был
`НЕ В СПИСКЕ: /uchi, /voroh-light, /yes-atlas`, итог `8/9`. После внесения трёх
маршрутов с ожиданиями, снятыми замером (`/voroh-light` — 5 полей, `/uchi` — 1,
`/yes-atlas` — 0), покрыты все тринадцать тем, итог `9/9`.

Список не выводится из `PATH_ROUTES` автоматически намеренно: ожидание «есть на
маршруте поля или нет» — осознанное решение человека, и подставить его машинно
значит вернуть ловушку «пустой набор = успех», ради которой третий элемент и
заводился.

**P1-2 закрыт машинно.** Заведена `yarn check:docs` (`tests/docs.check.mjs`):
номера диагнозов уникальны и идут подряд, ссылки «баг N» из `CLAUDE.md` и
`README.md` ведут на существующие. Обе ветки проверены негативным контролем —
возвращённый дубль номера 13 дал три находки сразу (дубль, пропуск 16, битая
ссылка в README), подставленный «баг 99» — битую ссылку в `CLAUDE.md`; обе с
exit 1.

**P2-1 закрыт.** У `FIXES.md` появилось оглавление по симптомам (номер нужен

**P2-2 закрыт.** Заведена `yarn check:registry` (`tests/registry.check.mjs`) —

архетипа тише всех остальных — ссылка открывается и показывает чужую раскладку.

Негативный контроль по каждой из четырёх веток: удалённый маршрут `/ewa` →
«тема есть, а ссылки на неё нет»; подменённый архетип → «маршрут объявляет

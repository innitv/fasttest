# Скриншот → тема подрядчика: сводка исследования

Дата: 2026-07-27. Тип: technology scouting (не стадия `01-research`, шесть артефактов research pack не собирались).
Собрано из четырёх параллельных ресёрчей: [01 — картинка в токены](01-image-to-tokens.md), [02 — vision в структуру](02-vision-to-structure.md), [03 — white-label темизация](03-whitelabel-theming.md), [04 — бренд по домену](04-brand-from-domain.md).

> **Дополнено полевой проверкой:** [05 — разведка пяти реальных подрядчиков](05-contractors-scan.md). Она уточнила два вывода этого документа. Первый: дешёвый шаг по домену (манифест, `theme-color`) на малом и среднем бизнесе почти не работает — ноль полезных попаданий из пяти, тогда как на банках было два из шести. Второй: главная кнопка действия у пяти сайтов из пяти оказалась нейтральной (чёрной или графитовой), а фирменный цвет живёт в акцентах — эвристика «цвет кнопки = цвет бренда», выведенная на VOROH, оказалась исключением, а не правилом. Доказательная база — в [evidence/](evidence/).

Повод: эксперимент дал ~74 % совпадения извлечённой темы с ручным эталоном по двум донорам. Измеримое (кегли, высоты, радиусы) попадает в 1–2 px; интерпретируемое (роль цвета, `pill` или число, обводка или заливка) ошибается заметно для глаза. Вопрос к исследованию: решал ли это кто-то до нас и как.

---

## Пять выводов, меняющих архитектуру

### 1. Готового решения нет ни у кого — это подтверждено, а не предположено

Три независимых отрицательных результата из трёх разных веток:

- **Инструмента, назначающего цветам UI-роли по растру, не существует** (01). Проверено по четырём категориям источников: npm-библиотеки квантования, библиотека Google, рецензируемая статья MDPI, коммерческие расширения. Везде роль назначает человек или LLM.
- **Геометрии по растру тоже нет** (01). Готового «дай PNG, получи `border-radius` в px» не нашлось — только рецепты OpenCV, поверх которых пишут вручную.
- **Ни один из пяти игроков жанра sales-демо не извлекает тему из скриншота или URL** (03). Storylane, Walnut, Navattic, Reprise, Demostack — везде точки замены размечает человек заранее. Свежие AI-фичи правят **уже размеченные** токены по текстовому промпту, а не распознают бренд с картинки.

Практический смысл: мы не переизобретаем забытое готовое. Но и скопировать не у кого — придётся строить.

**Важная оговорка про сложность входа.** В отчёте 01 всплыли Design Token Extractor и `dembrandt` — они извлекают токены успешно, но читают **вычисленный CSS из DOM живого сайта**, а не пиксели. Растр — самый трудный из возможных входов. Там, где есть доступ к странице, задача решена.

### 2. Наивный цикл самокоррекции не работает — гипотезу «система сама себя починит» надо похоронить

Это опровергает исходное предположение проекта о self-healing loop.

- **Design2Code (Stanford SALT lab)** — единственное найденное прямое измерение self-revision prompting («вот твой рендер, вот эталон, почини»): **минимальный или нулевой эффект** на всех моделях, кроме GPT-4V/Claude 3, и там минимальный.
- `abi/screenshot-to-code` (73.4k звёзд, MIT, активен) даёт агенту посмотреть на свой рендер **один раз** — это не цикл с количественным diff, а один взгляд «посмотри на себя».
- `tldraw/make-real` архивирован 20.02.2026, итерация там была ручной.
- Рабочие циклы существуют только там, где модель **дообучена под визуальную разницу как reward** (VisRefiner, UI2Code^N — оба препринты, не рецензированы). Даже там результат не улучшается монотонно с числом итераций: сходимость даёт **best-of-N отбор**, а не последовательная правка.

**Следствие для нас:** ставку надо делать не на «модель починит себя», а на внешний верификатор с численной метрикой плюс отбор лучшего из N попыток. Верификатор у нас уже написан — `tenant:diff` меряет близость к эталону по 13 осям. Не хватает только генерации нескольких кандидатов и выбора по метрике.

### 3. Извлекать надо мало, а генерировать много — и это индустриальная норма, а не компромисс

Сводка по числу параметров, которые крупные продукты реально открывают клиенту (03):

| Продукт | Параметров | Автоподбор остального |
|---|---|---|
| Stripe Checkout / Branding Settings | **4** | нет |
| Stripe Elements (Appearance API) | ~16 + `rules` | нет |
| Adyen Hosted Checkout Themes | **3** | нет |
| Chargebee Checkout | ~8–10 | нет |
| Paddle Checkout | ~10 | нет |
| **ЮKassa Widget** | **1–5** | **да** — остальное считает виджет |
| **Okta Sign-In Widget** | ~5 | **да** — вся палитра состояний из одного primary |
| Auth0 Universal Login | ~6–8 | нет |

Наши 60 полей — на порядок больше отраслевой нормы. Для полноэкранного демо это оправданно (мы показываем интерфейс целиком, а не встроенный виджет), но вывод для **генератора** прямой: не пытаться извлечь 60 значений, а извлечь 2–4 надёжно и вывести остальные алгоритмически.

**Здесь две ветки соединяются.** Отчёт 01 отверг Material Color Utilities: «он не читает роли с экрана, а генерирует новую схему из одного seed-цвета — это другая задача». Отчёт 03 показывает, что **ровно это и делает индустрия**: ЮKassa просит один `control_primary` и подбирает остальное сама. То есть MCU не бесполезен — он не нужен в первой половине пайплайна (чтение), но закрывает вторую (генерация согласованной палитры из немногих опорных цветов).

Разрыв, который надо зафиксировать честно: в обоих прецедентах опорные 1–2 цвета **вводит человек**, а не извлекает система. Шага «распознать цвет со скриншота» не делает ни один проверенный продакшн-продукт.

### 4. Конфликт «верность бренду против читаемости» решён, и решение стоит скопировать дословно

**Okta документирует** (не блог, а официальная документация продукта): вся палитра состояний кнопки выводится из одного Primary; виджет принудительно держит WCAG 1.4.3 (контраст текста ≥ 4.5:1); если Primary к белому не проходит — переключается цвет текста на чёрный. Числовой пример из документации: `#6B8A16` к белому даёт 3.98:1 (провал) → чёрный текст даёт 5.27:1 (проход). В третьем поколении виджета система **подстраивает сам Primary**, и точное сохранение введённого клиентом hex **не гарантируется и не считается регрессией**.

У нас уже есть `a11y_mode: enforced` — то есть направление верное. Не хватает явной, записанной политики: «если цвет донора не проходит контраст, система его подстраивает; это ожидаемое поведение». Сейчас это решается точечно и каждый раз заново.

### 5. Домен — дешёвый дополнительный вход, но не замена скриншоту

Живая проверка шести российских доменов, 27.07.2026 (04):

| Домен | Результат |
|---|---|
| `tbank.ru` | **точный цвет** `#ffdd2d` из `manifest.webmanifest` |
| `alfabank.ru` | **точный цвет** `#f03226` из `manifest.json` |
| `sber.ru` | домен — JS-заглушка с редиректом на другой домен, бренда нет |
| `vtb.ru` | манифест заявлен, но отдаёт 404; только иконки |
| `wildberries.ru` | антибот блокирует **и curl, и настоящий браузерный рендер** |
| `ozon.ru` | циклические редиректы, контент не получен |

Итог: 2 из 6 — точное попадание **без единой интерпретации**, просто чтение JSON. Это ровно закрывает главную боль эксперимента: `theme_color` в манифесте — уже готовая семантическая роль от самого бренда, а не наша догадка.

Три находки, которые важнее статистики:

- **`theme-color` в HTML врёт.** У Т-Банка там `#ffffff` (цвет хрома страницы), а настоящий фирменный жёлтый лежит только в манифесте. Тянуть только мета-тег — получить «измеренный, но не тот» цвет: тот же класс ошибки, что мы поймали на интерпретации скриншота.
- **Антибот бьёт по нашему основному классу подрядчиков.** Wildberries и Ozon — это ровно интернет-магазины, которым платёжный экран нужнее всего. Заблокированы оба.
- **`manifest.json` описывает бренд сайта, а не платёжного экрана.** Даже точный `theme_color` может отличаться от палитры конкретного чекаута. Эмпирически не проверялось.

Готовая библиотека под этот путь существует: **OpenBrand** (`tight-studio/OpenBrand`, MIT, 777 звёзд) — читает `theme-color`, манифест, доминирующие цвета логотипа, og:image, favicon. Её собственный разработчик документирует нерешённую проблему: **«цвет бренда» и «акцентный цвет дизайн-системы» инструмент не различает** — та же проблема ролей, что и у нас.

Про платные Brand API: **Clearbit мёртв** (закрыт 08.12.2025 после поглощения HubSpot). Logo.dev отдаёт цвета только на тарифе Pro ($1 260/год). Покрытие `.ru` у Logo.dev и Brandfetch **проверить не удалось** — оба требуют платного ключа, оба отказали на РФ-домене без него (401 и 302). Это честная дыра, а не отрицательный результат.

## Что из этого следует делать

Каскад входов вместо одного, с генерацией вместо извлечения:

1. **Домен, если он есть** — HTTP GET на `/manifest.json` и `/manifest.webmanifest`. Бесплатно, без ключей, даёт точный цвет там, где манифест есть и цел. Приоритет манифеста над HTML-мета-тегом (кейс Т-Банка).
2. **Скриншот как обязательный fallback** — для домена-заглушки, битого манифеста и антибота, то есть минимум для трёх сценариев из шести протестированных.
3. **Извлекать 2–4 опорных значения, а не 60.** Остальное выводить алгоритмически по прецеденту ЮKassa/Okta. Material Color Utilities годится как генератор согласованных тонов.
4. **Проверять внешним измерителем и отбором лучшего из N**, а не итеративной самокоррекцией — она измеренно не работает. `tenant:diff` уже написан.
5. **Записать политику контраста явно**, по образцу Okta: расхождение с hex донора ради читаемости — заявленное поведение, а не дефект.
6. **Оставить человека на подтверждении 5–8 полей**, которые ошибаются предсказуемо и воспроизводимо (роли цветов, `section_gap`, семантика радиусов, слот логотипа).

## Что осталось непроверенным

Перенесено из отчётов без смягчения:

- **Покрытие Brandfetch/Logo.dev по `.ru`** — требует платного ключа. Ни подтвердить, ни похоронить нельзя.
- **Отличается ли брендинг платёжного экрана от общесайтового `theme_color`** — логическое ограничение, эмпирически не проверялось ни на одном домене.
- **Русский текст именно на UI-скриншотах** — ни одной независимо проверенной цифры точности ни у одной открытой vision-модели (02). Есть смежные данные по документам.
- **Ни один датасет (Rico, VINS, Clay, WebSight) не покрывает русскоязычные мобильные платёжные экраны** (01) — заявленная точность моделей на наш материал не переносится. Это и объясняет разрыв между бенчмарками и нашими 74 %.
- **Бенчмарка «скриншот → тема-JSON» не существует** (02) — сравнивать себя не с чем, нужен собственный eval.
- Малый бизнес без манифеста и осмысленного `theme-color` — экстраполяция из выборки в шесть доменов, не измеренный факт.
- Frontegg, Descope, СБП, точные цифры Reprise/Demostack — не проработаны на уровне первоисточника (03).

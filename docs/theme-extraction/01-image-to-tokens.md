# Извлечение визуальных характеристик из растрового изображения UI

Technology scouting (не стадия `01-research`, шесть обязательных research-артефактов не собирались). Ось: что существует в мире для превращения скриншота интерфейса в структурированные визуальные данные — палитра, элементы, геометрия, датасеты. Дата обращения по всем источникам — 27 июля 2026.

## Краткий вывод

- **Главный отрицательный результат подтверждён**: ни одна найденная библиотека или статья не назначает извлечённым цветам семантическую UI-роль (фон/поверхность/текст/акцент/граница) на основе анализа готового чужого экрана. `node-vibrant` и `colorthief` дают перцептивные ярлыки (Vibrant/Muted/DarkVibrant и т. п.) — это не то же самое, что «это поле — фон карточки». Material Color Utilities и MDPI-модель 2024 года не читают роли с экрана, а **генерируют** новую схему ролей из одного seed-цвета — это принципиально другая задача, чем наша.
- **Детекция элементов интерфейса — рабочее направление, но заточено не под нашу задачу.** UIED (549 звёзд, CV-детектор без нейросети для графики) актуален только до июля 2021 и не даёт цвета/типографику. OmniParser (25.2k звёзд, активен по июль 2026) детектирует интерактивные регионы и подписывает иконки, но не извлекает токены дизайна — заточен под GUI-агентов, не под тему.
- **Геометрия (радиусы, отступы, сетки) как отдельная измерительная задача в вебе не решена никем** — везде это либо детекция bbox общего назначения (OpenCV/YOLO), либо ручной код поверх неё; готового инструмента «дай PNG, получи border-radius в px» не нашлось.
- **Датасеты (Rico, VINS, Clay, WebSight) обучены на другом материале**: англоязычные Android/iOS приложения или синтетические веб-страницы. Ни один не специализирован на мобильных платёжных экранах и не содержит русского текста — перенос точности на нашу задачу не подтверждён никем.
- **Практический вывод для нашего пайплайна**: измерительная часть (геометрия, кегли, отступы) закрывается собственными скриптами — так и предполагалось изначально, готового замену нет. Интерпретационная часть (роль цвета, тип виджета) у всех решается либо вручную, либо LLM-подсказкой — то есть наш эксперимент (vision-модель + собственные измерения) уже находится на переднем крае того, что публично существует, а не воспроизводит забытый готовый инструмент.

## 1. Палитра и назначение ролей цветам

### node-vibrant (Vibrant-Colors/node-vibrant)
Форк оригинального Android Palette API (алгоритм из `androidx.palette`), переписан на TypeScript. 2.4k звёзд, 113 форков, MIT-подобная лицензия (custom properties, файл LICENSE не проверен построчно), последний релиз npm — 6 месяцев назад (v4.0.4), репозиторий активен. Даёт 6 фиксированных «перцептивных» свотчей: `Vibrant`, `Muted`, `DarkVibrant`, `DarkMuted`, `LightVibrant`, `LightMuted`. Это категории по яркости/насыщенности, вычисленные квантованием (Median Cut / Wu), а не UI-роли — `Vibrant` может с равной вероятностью оказаться фоном баннера или акцентной кнопкой.

### colorthief / colorthief-node (lokesh/color-thief)
13.6k звёзд, 1.3k форков, MIT, полностью переписан в TypeScript в марте 2026 (v3). На вход UI-скриншота даёт: `getColor`/`getPalette` (медиан-кат по пикселям, поддержка OKLCH-квантования), и — важно для нашей задачи — `getSwatches()` с теми же категориями Vibrant/Muted, что и node-vibrant, плюс встроенные утилиты `isDark`/`isLight`, `textColor` (рекомендация чёрного/белого текста поверх цвета) и `.contrast` (WCAG-коэффициенты к белому/чёрному). Это ближайшее найденное приближение к «роли»: библиотека отвечает на вопрос «какой текст читается на этом фоне», но не на вопрос «это поле — фон карточки или подложка чипа». Есть отдельный CLI (`colorthief-cli`) и Node-порты (`color-thief-node`, 35 звёзд — маленький форк, для сравнения).

### Material Color Utilities (material-foundation/material-color-utilities)
2.2k звёзд, 211 форков, Apache-2.0, активен (issues за январь 2026). Ядро Material You: `Quantizer Celebi` (Wu quantizer → WSMeans) сжимает изображение до N доминирующих цветов, `score` ранжирует их по «пригодности для темизации», затем `scheme`/`dynamiccolor` **генерируют** полную ролевую схему (`primary`, `on-primary`, `surface`, `on-surface`, `tertiary` и т. д.) из ОДНОГО выбранного seed-цвета через алгоритмы HCT-пространства. Это не анализ существующего экрана: библиотека не решает «какой из шести серых на этом скриншоте — вторичный текст», она берёт один цвет и рисует новую, внутренне согласованную схему с нуля. Для нашей задачи (скопировать чужую тему, а не сгенерировать похожую) это архитектурно не то же самое, хотя может пригодиться как fallback-генератор недостающих тонов.

### MDPI: Automated Image-Based User Interface Color Theme Generation (2024)
`https://www.mdpi.com/2076-3417/14/7/2850` — рецензируемая статья, но по методу идентична MCU: извлекает доминирующие цвета из образа (например, логотипа) и подбирает тему, балансируя гармонию и контраст. Тоже генерация, не считывание существующих ролей с готового интерфейса.

### Ответ на прямой вопрос задания
Инструмента, который **читает** экран и **классифицирует** уже присутствующие на нём цвета по ролям (фон/поверхность/текст/акцент/граница), в открытом или дискутируемом виде найти не удалось — ни в библиотеках квантования, ни в академических статьях по CHI/цветовым темам. Единственные найденные примеры «автоматизации ролей» — Chrome-расширение Design Token Extractor и утилита `dembrandt` (см. раздел «применимость») — но обе читают **вычисленный CSS из DOM живого сайта**, а не пиксели растра, и поэтому неприменимы к «скриншот чужого экрана, у которого нет доступа к коду». Везде, где роль всё же назначается на растровом материале, это делает человек или инструктированная vision-LLM (см. промпт-шаблоны вроде aiuxplayground «Extract Design System from Screenshot») — то есть ровно то, что мы уже делаем сами. Отрицательный результат подтверждён по независимым источникам разных категорий (npm-библиотеки, Google-библиотека, MDPI-статья, коммерческие расширения) — совпадение не случайно.

## 2. Детекция элементов интерфейса

### UIED — MulongXie/UIED
549 звёзд, 125 форков, Apache-2.0, репозиторий помечен «Upgraded on 5/July/2021» и с тех пор фактически не развивается (README прямо говорит «may be updated irregularly»). Гибридный подход без нейросети для графических элементов: старый CV (edge/contour detection) для кнопок/картинок/полей ввода + Google Cloud OCR для текста + CNN-классификатор (13 классов: Button, CheckBox, EditText, Image, ImageButton, RadioButton, Switch и т. д.) для non-text компонентов. Статьи: «UIED: a hybrid tool for GUI element detection» (ESEC/FSE 2020, ~152 цитирования по Semantic Scholar) и «Object Detection for GUI: Old Fashioned or Deep Learning or a Combination?» (arXiv:2008.05132). Точные цифры precision/recall из оригинальной статьи извлечь не удалось (PDF недоступен по найденной ссылке) — точность из README **не проверялась независимо**. Экспортирует детекции в JSON с bbox и типом — потенциально полезно как источник bbox-разметки для последующего измерения геометрии, но не даёт цвета/токены.

Форк-экосистема жива за счёт производных: `UI2CODE` (тот же автор, реверс-инжиниринг UI→код) и сторонние обёртки вроде `AIgrator/ueId_easyocr` (UIED + EasyOCR, свежий форк, но фактически 1 коммит).

### OmniParser — microsoft/OmniParser
25.2k звёзд, 2.2k форков. Лицензия комбинированная: код репозитория — CC-BY-4.0, веса YOLOv9-детектора (`icon_detect_v3`) — MIT, более старые Ultralytics-based детекторы — AGPL (унаследовано от YOLO), caption-модели (Florence-based) — MIT. Активная разработка: последнее обновление в новостях README — июль 2026 (YOLOv9-E детектор). Метод: детекция интерактивных регионов (fine-tuned YOLO) + captioning модель (Florence-2/BLIP2), объединяющая функциональное описание иконки с координатами — специально для того, чтобы GPT-4V/vision-агент мог кликать по правильному месту экрана. Заявленный автором результат — 39.5% на ScreenSpot Pro (v2, релиз 2025/1), **на бенчмарке от независимой команды** (`ScreenSpot-Pro: GUI Grounding for Professional High-Resolution Computer Use`, `arxiv.org/abs/2504.07981` / `likaixin2000.github.io`), но сравнительную таблицу этого бенчмарка составляли для других моделей-грундеров (OS-Atlas, UGround, GPT-4o) — прямого числа OmniParser в опубликованной таблице ScreenSpot-Pro не нашлось, только собственное заявление Microsoft о SOTA. Для нашей задачи полезность ограничена: OmniParser отвечает «где кликабельный элемент и что он делает», а не «какого цвета этот элемент и какой у него border-radius» — придётся комбинировать с отдельным измерением.

### Ferret-UI / Ferret-UI 2 (Apple)
arXiv:2404.05719 (ECCV 2024) и arXiv:2410.18967 (ICLR 2025), код и веса — `github.com/apple/ml-ferret` (лицензия ограничена исследовательским использованием, наследует условия LLaMA/Vicuna/GPT-4, датасет CC BY-NC 4.0 — **коммерческое использование запрещено**). MLLM для referring/grounding задач на мобильных UI (iPhone, Android, iPad, Web, AppleTV в версии 2). Заявленные автором метрики (Table в статье Ferret-UI 2, ICLR 2025): Widget Classification 79.1–83.6% в зависимости от платформы, Find Widget 86.4–88.6%, OCR 69.3–80.5% — все цифры **заявлены авторами**, независимой проверки третьей стороной не нашлось. Лицензионное ограничение делает модель неприменимой к нашему коммерческому демо напрямую.

### Screen Recognition (Apple, CHI 2021)
`arxiv.org/abs/2101.04893`, ~241 цитирование. Датасет: 77 637 экранов из 4068 приложений iPhone (собран и размечен вручную). Заявленная точность (порог IoU > 0.5): **71.3% mean AP** невзвешенно, **82.7% weighted mean AP** с весом по частоте типа элемента в датасете, на тестовой выборке 5002 скриншотов, 13 типов UI. Модель и веса не выложены в открытый доступ (это внутренняя технология VoiceOver, не опенсорс-репозиторий) — годится только как ориентир по порядку точности задачи, не как инструмент, который можно установить.

### ScreenAI (Google, IJCAI 2024)
arXiv:2402.04615. Vision-language модель на архитектуре PaLI + patching-стратегия pix2struct, 5B параметров, заявлен SOTA на WebSRC/MoTIF среди моделей сравнимого размера. Не нашли открытых весов модели в свободном доступе (Google Research публикует датасеты Screen Annotation/ScreenQA, но не факт что веса модели открыты) — требует отдельной проверки перед использованием, помечаю `нужна проверка`.

## 3. Геометрия (радиусы, отступы, сетки, высоты строк)

Готового инструмента «скрипт/библиотека, дай PNG — получи border-radius/padding/line-height в px» найти не удалось ни в виде open source проекта, ни в виде коммерческого продукта. Всё, что нашлось по смежным запросам, — это:
- общие туториалы OpenCV про измерение объектов через `minAreaRect` и эталонный объект (Roboflow blog «How to Measure Object Size with Computer Vision») — применимо к физическим объектам на фото, не к UI-примитивам;
- обсуждения на Reddit/Facebook про детекцию углов (`cv2.approxPolyDP`, Hough Circle) для конкретных прикладных задач — не готовый инструмент, а рецепт «напиши сам»;
- инструменты «скругли углы у картинки» (vayce.app, pinetools) — обратная задача (наложить радиус), не измерение существующего.

Это подтверждает наш собственный вывод из эксперимента: то, что измеряется (высоты строк, кегли, радиусы) действительно не имеет готовой библиотеки-конкурента — весь мир решает это либо через DOM/CSS инспекцию (неприменимо к чужому скриншоту без доступа к коду), либо пишет измерительный код вручную поверх детекции границ (наш путь). Точка роста здесь — не поиск замены, а собственная калибровка (что мы уже подтвердили: ±5% в масштабе, точность 1–2px).

## Применимость к нашей задаче

**Что реально снимет часть боли:**
- `colorthief` v3 (свежий, MIT, активно поддерживается) — если нужно быстро получить кандидатов на роль «текст поверх этого фона», его `textColor`/`.contrast`/`isDark` дают то же самое решение, которое мы сейчас, вероятно, получаем от vision-модели дороже. Стоит попробовать как дешёвый pre-filter перед LLM-интерпретацией: он не назначит роль «pill background», но подскажет контрастность и перцептивную категорию (Vibrant/Muted) для каждого кандидата-цвета, сузив то, что LLM должна интерпретировать.
- Экспорт bbox из UIED (даже устаревшего) в теории мог бы дать грубую сетку кандидатов на «где искать радиус/отступ», но актуальность кода 2021 года и отсутствие развития — риск, что придётся чинить самим; выигрыш не гарантирован относительно наших уже написанных измерительных скриптов.

**Что не снимет боль (и почему это важно осознать):**
- OmniParser/Ferret-UI/ScreenAI решают смежную, но другую задачу — grounding и captioning для агентов, управляющих интерфейсом, а не извлечение дизайн-токенов. Использовать их как «детектор виджетов» для темизации потребует отдельного слоя интерпретации поверх их вывода — то есть именно ту же самую нерешённую проблему (какая из шести серых зон — `pill`), которую мы уже пытаемся решить своими средствами.
- Ferret-UI лицензионно закрыт для коммерческого использования (CC BY-NC 4.0 датасет, ограничения LLaMA/Vicuna) — юридически неприменим к продакшн-демо подрядчиков без отдельного разрешения.
- Ни один датасет не покрывает домен (мобильные платёжные экраны, русский язык) — дообучение любой из моделей потребует собственной разметки, что by design то же самое усилие, которое мы уже вложили в ручной эталонный конфиг.
- Главный вывод: **назначение семантической роли цвету и типу виджета везде на границе исследования, а не решённая задача с готовой библиотекой.** Наш путь (vision-модель + собственные измерения + ручная валидация 74%) — это не изобретение велосипеда, а рабочая точка на переднем крае того, что публично существует. Инвестировать стоит не в поиск замены, а в сужение LLM-интерпретации специализированными подсказками (например: явный список «это поле — текст, эта заливка — pill» через few-shot примеры из уже собранных вручную конфигов) и в дешёвые CV pre-filter'ы (contrast/isDark из colorthief) перед дорогим шагом интерпретации.

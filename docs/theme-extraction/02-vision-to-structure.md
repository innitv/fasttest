# Vision-модели → строгий структурированный вывод: скаутинг технологий

Дата: 2026-07-27. Тип: technology scouting (не `01-research` продуктового workflow, run-ledger не ведётся). Инструменты: Tavily search/extract (основной источник), без WebFetch/WebSearch в этом заходе.

## Краткий вывод

Ни один найденный screenshot-to-code проект не реализует полноценный автоматический цикл «сгенерировали → отрендерили → сравнили → починили»: `abi/screenshot-to-code` даёт агенту посмотреть на свой рендер один раз (опциональный Playwright-скриншот), `tldraw/make-real` вообще архивирован и итерация там ручная (человек дорисовывает и жмёт кнопку заново). Единственное прямое измерение self-revision prompting (Design2Code, Stanford NLP) показало **минимальный или нулевой эффект** от «вот твой рендер, вот эталон, почини» на всех моделях кроме GPT-4V/Claude 3 (и там — минимальный). Рабочие циклы самокоррекции существуют только там, где модель **дообучена** под визуальную разницу как reward (VisRefiner, UI2Code^N, оба — препринты 2025-2026) — и даже там результат «текущего» прохода не монотонно улучшается с числом итераций, сходимость даёт только best-of-N отбор поверх итераций. Наша собственная находка про обрезание `minimum`/`maximum`/`pattern` в JSON Schema независимо подтверждена (Claude strict mode явно отбрасывает эти ключевые слова, Gemini молча игнорирует неподдерживаемые) — это системное свойство API всех трёх вендоров, а не баг нашей интеграции. Открытых vision-моделей с проверенной независимо точностью именно на **русском тексте в UI-скриншотах** не нашёл — есть только смежные данные (документы, не интерфейсы) и анекдотические отзывы практиков.

## 1. Screenshot-to-code проекты

### abi/screenshot-to-code
github.com/abi/screenshot-to-code — 73.4k звёзд, MIT, активно развивается (коммиты владельца датированы «вчера», «2 дня назад», «3 дня назад» на момент обращения). Генерирует HTML/Tailwind/React/Vue из скриншота через GPT-4o/Claude/Gemini, опционально Replicate для картинок. Механизм самопроверки описан в README дословно: «Screenshot preview (optional) lets the agent render its own generated page in a headless browser and visually check its work» — то есть один прогон рендера через Playwright/Chromium, который агент разглядывает визуально; это **не** автоматический цикл с количественным diff и повторными правками, а один shot «посмотри на себя». Issue #17 «Investigate open source models» открыт с ноября 2023 года и по сей день не закрыт — проект как был, так и остаётся завязан на платные API, встроенной поддержки локальных VLM нет.

### tldraw/make-real
github.com/tldraw/make-real — репозиторий **архивирован владельцем 20 февраля 2026**, дальше не поддерживается. Механизм (по стартер-репо и блогу tldraw): рисуешь UI на канвасе → скриншот выделения → отправка в GPT-4V с промптом «ты веб-разработчик, тебе дали вайрфрейм» → HTML-ответ кладётся в iframe на канвасе. Итерация — **ручная**: чтобы модель видела свой предыдущий результат (iframe для неё «чёрный ящик»), ей передают обратно тот же HTML с пометкой «заполни этот белый прямоугольник»; следующий шаг запускает пользователь кнопкой «Make Real» после аннотирования скриншота. Автоматического render-compare-fix нет. Лицензия tldraw SDK с 2024 года — некоммерческая без отдельной покупки лицензии (tldraw.dev/blog/license-update-for-the-tldraw-sdk), это ограничивает использование кода как референса для коммерческого продукта.

### OpenUI — коллизия имён, два разных проекта
`wandb/openui` (Chris van Pelt, Weights & Biases) — 22.5k звёзд, Apache-2.0, живой (issues открываются вплоть до июня 2026). Это оригинальный screenshot/text → live HTML/Tailwind проект в духе v0.
`thesysdev/openui` — **другой** проект под тем же именем: коммерческий "OpenUI Lang", собственный компактный DSL для потокового рендера сгенерированного UI (компонентная библиотека → системный промпт → LLM отвечает в OpenUI Lang → рендерер). Не про скриншоты вообще — это про генерацию UI из текстового промпта в заранее заданном компонентном словаре. Пересказы, где два проекта путают, встречаются в поиске — при использовании этого имени в дальнейшем ресёрче держать оговорку явно.

### v0 (Vercel)
Закрытый коммерческий продукт. В этой сессии инженерных деталей внутреннего устройства (промпт, механизм правок, наличие визуального diff-цикла) не нашёл — только маркетинговые страницы Vercel и обзорные видео пользователей. Статус: **не проработано** инженерно, только фактография «что это» на уровне продукта.

### Design2Code как эталон, не продукт
github.com/NoviScl/Design2Code (Stanford SALT lab) — 588 звёзд, код MIT / данные ODC-By. Это не screenshot-to-code инструмент, а **бенчмарк и экспериментальный харнесс** (484 реальных веб-страницы + 80 «HARD» из GitHub Pages), на котором тестировали GPT-4V, Gemini Pro Vision, Claude 3.5 и дообученную Design2Code-18B. Именно на этом харнессе получено ключевое для нас измерение self-revision prompting (см. раздел про самокоррекцию).

## 2. Structured output на практике

Наша находка (числовые ограничения и `pattern` до модели не доезжают, проверка — только на клиенте) подтверждается независимо, а не единичным анекдотом:

- **collinwilkins.com/articles/structured-output** (обновлено май 2026, снабжена таблицей по провайдерам): «Claude's strict mode rejects more of the JSON Schema spec than OpenAI's: no recursive schemas, no minimum/maximum, no string length constraints, no external $ref. Those checks have to move into Pydantic post-validation instead of the schema itself.» И отдельно про Gemini: «unsupported keywords are silently ignored. No error, no warning — the model just returns JSON that doesn't match your schema.» Это ровно наша ситуация: границы `minimum`/`maximum` не доходят ни до Claude (отклоняются явно в strict mode), ни до Gemini (молча игнорируются), проверка неизбежно переезжает на клиент.
- OpenAI-форум (community.openai.com, темы «Strict mode does not enforce the JSON schema?» и «Structured Outputs not reliable with GPT-4o-mini and GPT-4o») подтверждает, что даже там, где схема вроде бы валидна, модель может не соблюсти её (пропущенные поля, спутанные типы) — то есть «структурированный вывод» гарантирует формат в лучшем случае, не гарантирует семантику ни у одного из трёх крупных вендоров.

Практические приёмы, которые реально используют (собраны из нескольких независимых источников, не одного гайда):

1. **Дублировать границы в тексте промпта** — раз `minimum`/`maximum`/`pattern` на уровне схемы не работают у части моделей, единственный канал их довести до модели — явный текст инструкции; финальная проверка всё равно остаётся на клиенте (Pydantic/Zod). Это уже есть в нашей архитектуре (жёсткие клампы в zod); подтверждается как стандартная практика, а не как временный костыль.
2. **Retry с текстом именно валидационной ошибки**, а не общим «попробуй ещё раз» — lawzava.com (2024-04-29, гайд по Go) и тред r/LocalLLaMA «feed the validation error back into the retry» сходятся: описывать ошибку для модели («field X must be an int, you sent a string»), возвращать её же прошлый вывод как объект для правки, ограничивать число попыток. Явное предупреждение из реддит-треда: возврат модели её же прошлого вывода может «заякорить» её — она поправит только названное поле и не тронет остальное, либо будет пинг-понговать между двумя неверными ответами; средство — echo-ить только невалидный фрагмент + нарушенное правило, а не весь блок, и на retry снижать температуру / включать constrained decoding.
3. **Дробление схемы на несколько вызовов** — dev.to «LLM Structured Output in 2026»: «Complex schemas are expensive. Break them into smaller, parallelized calls» — прямая рекомендация не пытаться вытащить все ~60 полей одним вызовом.
4. **Constrained decoding (grammar-based)** — принципиально другой уровень решения: Outlines, XGrammar (mlc-ai/xgrammar, GitHub), Guidance/llguidance (Microsoft), llama.cpp GBNF. Работают не через промпт и постпроверку, а через маскирование недопустимых токенов на этапе сэмплинга — синтаксическая валидность (закрытые скобки, обязательные поля, принадлежность enum) становится не «маловероятной ошибкой», а **структурно невозможной**. JSONSchemaBench (упоминается в нескольких источниках как независимый бенчмарк на ~10 000 реальных JSON Schema, тестирует Guidance/Outlines/XGrammar/OpenAI) — не проверял лично, детали `нужна проверка`. Важная оговорка, задокументированная BAML: constrained decoding даёт **гарантию формата, не гарантию семантики** — их пример: модель вернула `1` вместо `0.46` для количества в задаче извлечения из чека, потому что схема требовала числовое поле, а свободный текстовый вывод дал правильное число; итоговая точность 91.37% (constrained) против 93.63% (free-form) на их тестовом наборе. Это значит: даже если бы мы переключились на self-hosted constrained decoding, наш кламп-слой на клиенте всё равно не исчезает — grammar решает другой класс ошибок (сломанный JSON), не тот, что мы наблюдали (интерпретационные ошибки внутри допустимого диапазона).
5. Контекст для agentic-конвейеров: спецификация MCP с ноября 2025 требует, чтобы tool-серверы возвращали структурированный результат, соответствующий output schema — то есть требование строгого вывода расширяется за пределы одного вызова модели.

Не проверено в этой сессии: поддерживают ли Outlines/XGrammar/Guidance принудительное сужение диапазона чисел (`minimum`/`maximum`) на уровне грамматики, а не только тип/enum/обязательность полей — не нашёл прямого источника, помечаю `нужна проверка`, не утверждаю ни да, ни нет.

## 4. Бенчмарки

Прямого бенчмарка «скриншот → структурированная тема/стиль JSON» (наша задача) не существует. Ближайшие по форме:

- **ScreenSpot / ScreenSpot-v2** (Cheng et al.) — GUI grounding: 1272 инструкции, mobile/desktop/web, элемент текстовый или иконка; успех = предсказанная точка попала в bbox эталона. Это про «найди элемент», не про «опиши его стиль», но замеряет ту же способность видеть структуру интерфейса.
- **ScreenSpot-Pro** (likaixin2000, GitHub + PDF) — жёстче: аутентичные задачи из 26 профессиональных десктоп-сред (Photoshop, AutoCAD, IDE и т.п.), высокое разрешение. На нём точность резко падает по сравнению с обычным ScreenSpot: лучшие 7B-модели с верификатором — около 44-48%, тогда как на исходном ScreenSpot те же модели дают 88-92%. Это прямое предупреждение для нас: плотные, «настоящие» интерфейсы обваливают точность моделей сильнее, чем чистые демо-скриншоты, на которых обычно меряют бенчмарки.
- **Design2Code / Design2Code-HARD** (Stanford SALT lab) — скриншот → HTML, метрики: CLIP-эмбеддинг similarity (high-level) + block-match/text/position/color matching по bounding box (low-level), авторы показали корреляцию этих метрик с человеческой оценкой.
- **VisualWebBench** — grounding элементов как multiple-choice, отдельная методика.

Встретил в поиске страницу-агрегатор «benchlm.ai» с лидербордом Design2Code (упоминает «GLM-5V-Turbo», «Claude Opus 4.6» и проценты без прослеживаемой методологии) — **не включаю как источник**: это сторонний агрегатор без видимой верификации данных, а не первичный бенчмарк-репозиторий; настоящий Design2Code лидерборд — это результаты из статьи Si et al. и репозитория NoviScl/Design2Code.

## Цикл самокоррекции: что реально работает

Это была главная гипотеза, ради которой стоило искать, и ответ получился яснее, чем ожидалось:

**Наивный prompting-цикл («вот твой рендер, вот эталон, укажи разницу и почини») почти не работает.** Прямое измерение из статьи Design2Code (Si et al., Stanford NLP, цитата из PDF): self-revision prompting «has some minor improvement on block-match and position similarity for GPT-4V and Claude 3, but brings no improvement on Gemini Pro Vision and all other open-source models, potentially due to the limited capabilities of LLMs to do self-revision». То есть даже у топовых закрытых моделей 2024 года эффект был минимальным, а у Gemini и у всех открытых моделей — нулевым. Причина, которую называют авторы, ровно та, что интуитивно ожидаема: сравнение двух изображений и перевод разницы обратно в правки кода — задача сложнее, чем просто сгенерировать код по одному скриншоту с добавлением текстового описания элементов (text-augmented prompting, которое действительно помогает).

**Рабочие циклы существуют — но это не prompting-трюк, а дообучение под конкретный reward.** Два независимых препринта (оба свежие, оба **не рецензированы**, статус — «предварительный результат», не устоявшийся факт):
- **UI2Code^N** (arXiv 2511.08195, ноябрь 2025 → обновления до v4) переформулирует задачу как «interactive visual optimization»: черновик → рендер → правка по видимой разнице, с явным test-time scaling — заявлено +12% за четыре раунда полировки, при этом на синтетических данных эффект насыщается уже к N=3 раундам, а на реальных веб-страницах продолжает расти до N=5 (авторы объясняют это большей структурной сложностью реальных страниц).
- **VisRefiner** (arXiv 2602.05998, 2026, препринт) обучает модель через GRPO с наградой на основе CLIP-similarity между рендером и эталоном, специально под render-compare-revise. Но их же собственный анализ многоходовой самокоррекции честно фиксирует: «results begin to fluctuate as the number of refinement turns increases... additional iterations do not consistently yield better quality once major discrepancies have been corrected» — то есть у текущего (last-turn) результата **нет монотонной сходимости**; растёт только «filtered» показатель — теоретический максимум, если выбирать лучший из всех промежуточных вариантов по CLIP-скору (у них это доходит до 94.2 к 5-му раунду). Иными словами, чтобы итерации реально помогали, нужен внешний селектор/верификатор поверх модели, а не доверие к тому, что модель сама «поймёт, что стало лучше».

**Метрики, которыми реально меряют** это в исследовательской литературе — не «судейство LLM», а количественное сравнение изображений: CLIP-эмбеддинг similarity (общее визуальное сходство) плюс низкоуровневый набор Design2Code — bounding-box matching, сравнение текста, позиции и цвета совпавших элементов; человеческую оценку используют только как проверку корреляции метрик, не как runtime-сигнал для самого цикла. Классический pixel-diff / SSIM инструментарий (dev.to, «Screenshot Diffing») — из совсем другого мира (visual regression testing CI), там же явно предупреждают про шум от антиалиасинга и разного рендеринга шрифтов между ОС — тот же шум будет мешать и в нашем случае, если сравнивать чужой оригинальный скриншот с нашим рендером демо-стенда напрямую.

**Что из этого реально шло в прод.** Единственный шипнутый продукт с автосамопроверкой, который нашёл, — это опциональный «screenshot preview» у abi/screenshot-to-code, и это не render-compare-fix цикл, а однократный визуальный self-check («вот твой рендер, посмотри сам глазами модели, без числовой метрики и без гарантированного повторного прохода»). Разрыв между тем, что показывают research-препринты (обученные модели с GRPO-наградой на CLIP), и тем, что реально есть в открытых инструментах (один опциональный взгляд на свой рендер), — большой.

## Применимость к нам

- **Ожидания от «render → compare → fix» нужно снизить.** Наивная версия («попроси модель сравнить свой рендер с оригиналом и исправить») по независимому измерению почти не работает даже на GPT-4V/Claude — рассчитывать, что тот же приём вытянет нашу интерпретационную точность (74% → выше) без дополнительной инженерии, не стоит.
- **Рабочая версия цикла требует внешнего верификатора, не доверия к самооценке модели.** У нас он уже есть в зачаточном виде — измерительные скрипты, которые дают точность 1–2 px по измеримым полям. Практический шаг, подтверждённый и исследованиями (VisRefiner: улучшение только через best-of-N отбор по внешней метрике), и практикой structured output (лов reddit: «feed the validation error back», не общее «попробуй ещё»): гонять несколько кандидатных извлечений и выбирать через существующий измерительный скрипт как через CLIP-score в VisRefiner, а не просить модель саму признать ошибку интерпретационных полей (какой это серый, pill или число).
- **Обрезание `minimum`/`maximum`/`pattern` — это системное свойство API, а не наш баг.** Независимое подтверждение (collinwilkins.com, OpenAI community threads) снимает вопрос «мы что-то делаем не так» — граница между Claude/Gemini/OpenAI и нашей zod-схемой физически необходима при любой реализации. Единственное, что стоит добавить сверх уже сделанного: не просто молча клампить на клиенте, а при выходе значения за диапазон логировать это как «модель промахнулась мимо разрешённого диапазона» (retry с текстом именно этой ошибки, а не тихий клип) — это дешёвый шаг, который несколько независимых источников называют стандартной практикой.
- **Constrained decoding — не бесплатный апгрейд для нашего конкретного бага.** Даже если самостоятельно хостить модель с Outlines/XGrammar/Guidance, задокументированный BAML-кейс показывает: грамматика гарантирует форму, не гарантирует, что число внутри допустимого диапазона — правильное число. Наш кламп-слой на клиенте не заменяется этим переходом, он остаётся необходим.
- **Открытая vision-модель как замена платному API — под вопросом именно для русского UI.** Ни один найденный источник не даёт проверенной точности на русском тексте в интерфейсах (только на документах — Habr, и анекдотически — Reddit). Если это направление берётся всерьёз, нужен собственный небольшой eval на 10-20 реальных скриншотах наших же подрядчиков, а не перенос вендорских чисел с OCR-бенчмарков документов. Кандидат для такого eval — Qwen-VL 7-8B (единственная линейка с хоть каким-то независимым измерением и подтверждённой работой на одной потребительской карте).
- **ScreenSpot-Pro — предупреждение, не повод для паники.** Разрыв в точности между «чистым» ScreenSpot и «профессиональным» ScreenSpot-Pro (88-92% → 44-48%) для нас значит: платёжные экраны конкурентов с плотной версткой (мелкие radio/чекбоксы, многострочные условия) вероятно ближе по сложности к Pro-режиму, чем к учебным демо — наши уже измеренные ~74% совпадения стоит интерпретировать в этом контексте как правдоподобный, не заниженный результат.
